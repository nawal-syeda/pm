# SQLite database design

The proposed schema is recorded in [database-schema.json](database-schema.json). It is normalized around four entities:

- `users` stores accounts and gives the model room for multiple users.
- `boards` stores one board per user for the MVP.
- `columns` stores the board's fixed stages and their order.
- `cards` stores cards and their order within a column.

## Integrity rules

SQLite foreign-key enforcement must be enabled on every connection with `PRAGMA foreign_keys = ON`. Board ownership is enforced through `boards.user_id`; API queries must always select a board through the authenticated user. Foreign keys cascade from user to board, board to columns, and columns to cards so deleted parents cannot leave orphaned rows.

The unique `boards.user_id` constraint enforces one board per user. The `(board_id, position)` and `(column_id, position)` constraints make order explicit and prevent duplicate positions within a parent. Positions are zero-based integers and are rewritten inside a transaction when a card or column is moved or reordered.

All timestamps are UTC ISO 8601 text. IDs are opaque text values generated by the backend. Usernames, column titles, card titles, and board names must be non-empty after trimming.

## Initialization and local file

Part 6 will create the database directory and file if they do not exist, execute the schema in a single initialization step, enable foreign keys, and idempotently seed the MVP user, board, five columns, and demo cards. The planned default file is `data/project_management.sqlite3` relative to the application working directory. The `data/` directory and database files must remain outside the Docker image layer and be mounted as a persistent volume when container persistence is needed.

Initialization and seed operations must be safe to run repeatedly. Existing rows are identified by their stable IDs or unique keys and are not duplicated.

## Transactions and board operations

Each direct mutation runs in a transaction. A move or reorder updates affected positions together and commits once. Future AI requests will validate every requested operation first, apply all operations in one transaction, and roll back the complete request if any operation is invalid.

The API returns the public board shape from `database-schema.json`; it does not expose user rows, session tokens, internal timestamps beyond the board's `updated_at`, or database implementation details.

## Review scenarios

The model supports column rename, card create, edit, move, reorder, and delete. It also supports an atomic request containing multiple of those operations. Ownership is checked before every read and mutation, and cascading deletes preserve referential integrity.
